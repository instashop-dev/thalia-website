What is PHP2Shell?

PHP2Shell is a shorthand name used for CVE-2026-109618 and CVE-2026-109619. Public security advisories describe the issues as critical vulnerabilities that can affect PHP installations serving web requests. The PHP project’s fixed PHP 8.3 release is 8.3.36.

The important operational detail is that these flaws sit in the PHP runtime layer. A theme setting or ordinary application-code patch cannot replace updating the interpreter, package, container image, or managed runtime that actually serves requests. The operator responsible for that runtime must confirm that the patched version is the one handling live traffic.

Security releases also need careful communication. A vulnerability name can sound alarming, but the potential impact of an unpatched component and the evidence found in one environment are different questions. A useful customer update explains both without turning an investigation finding into an absolute guarantee.

Why upgrading PHP was the right remediation

For the affected Thalia environment, the change was from PHP 8.3.22 to PHP 8.3.36. That version target aligned with the fixed PHP 8.3 release. The Plesk advisory also points administrators to fixed PHP branches or the patched package supplied by their distribution.

For teams managing their own systems, the exact update command depends on the operating system, package repository, container image, and process manager. The safe pattern is consistent: use a trusted fixed package or image, redeploy the process serving traffic, and verify the running version rather than relying only on a build file.

WAF rules can add defense in depth, but they are not a substitute for patching. Cloudflare’s PHP2Shell guidance makes that distinction clear. The primary remediation is to update the vulnerable runtime, make sure the updated process serves live traffic, and then verify both security state and application health.

How we handled the PHP security update

1. Identify the affected runtime and scope

We identified the application environment using PHP 8.3.22 and reviewed which products shared it. The scope included Thalia’s Shopify apps and other products connected to the affected application environment.

Scope matters in a runtime incident. Updating one service does not automatically update a second container, scheduled worker, or separate application environment. We treated PHP as an environment-level dependency and reviewed the products using it.

2. Apply the fixed release and security patches

We upgraded PHP from 8.3.22 to 8.3.36 and installed the required security patches. The goal was to move the serving environment to the fixed release, not merely to add a temporary request filter.

Teams should also confirm that the change reaches every process that can serve requests. A patched local shell, an updated build file, or a newly created image is not enough if an older worker or origin process remains active.

3. Verify application behavior after the change

A security patch is not complete until the application still works. After the upgrade, our team confirmed that the fixes were active, the application loaded successfully, and expected functionality remained available.

This step catches a different kind of risk: an urgent update can create outages, dependency errors, or broken integrations. The right post-update review covers both the security state and the merchant experience.

4. Review available evidence

We reviewed available server logs for attempted exploitation, suspicious activity, or unexpected access patterns related to the issue. No such signs were identified during our investigation.

That finding should be read precisely. The available logs showed no evidence of merchant-data access or leakage connected to this issue. It is not a universal guarantee for every PHP environment or every organization.

5. Communicate merchant impact

The update did not change existing merchant data, login credentials, or application settings. Merchants do not need to reinstall the apps, migrate their stores, or change their configuration because of this runtime update.

What this means for Shopify merchants

Most Shopify merchants do not administer the PHP runtime behind a hosted app. That responsibility belongs to the app operator or hosting provider. Merchants should still pay attention to security notices, especially when a provider asks them to update an app, rotate credentials, or review an integration.

For this Thalia update, no merchant action is required. Merchants can continue using the applications as usual. If something unexpected appears, contact support with the app name, store context, approximate time, and a description of the behavior.

Why “no evidence found” is the accurate security language

Security communication becomes less trustworthy when it promises more than an investigation can establish. “No merchant data will be leaked” is an absolute future guarantee. A responsible statement describes the controls applied, the evidence reviewed, and the conclusion supported by that evidence.

For this issue, the accurate conclusion is that the affected runtime was patched, application functionality was verified, available logs were reviewed, and no evidence of merchant-data access or leakage was found in connection with the issue. Thalia will continue monitoring its infrastructure and applying necessary security updates.

What engineering teams should verify after a runtime patch

A version number is a useful starting point, but it is not the entire verification plan. Teams should confirm the package installed on the host, the image deployed to production, and the process that is actually receiving web traffic all point to the same patched release.

  • Confirm the serving process. Check PHP-FPM, Apache, LiteSpeed, or the relevant runtime process rather than only the command-line PHP binary.
  • Restart or redeploy where required. Long-running workers can continue using an older binary until they are restarted.
  • Test normal requests. Verify login flows, app loading, API calls, background jobs, and the integrations merchants depend on.
  • Preserve investigation evidence. Keep the relevant deployment record, version output, health checks, and log-review notes together.
  • Define the communication boundary. Separate what was changed, what was observed, and what remains under monitoring.

This approach also makes future maintenance easier. When another runtime advisory arrives, the team has a known inventory, a repeatable deployment path, and a clear set of checks instead of starting from a blank page.

PHP2Shell FAQ

What is PHP2Shell?

PHP2Shell is the common name for CVE-2026-109618 and CVE-2026-109619, two critical PHP vulnerabilities. The PHP project released fixed versions, including PHP 8.3.36.

Does PHP 8.3.36 fix PHP2Shell?

Yes. PHP identifies 8.3.36 as the fixed PHP 8.3 release. Operators should verify that the runtime serving web requests is the patched one.

Do Shopify merchants need to update their stores?

Merchants generally do not manage the PHP runtime behind a hosted Shopify app. They should follow instructions from their app and hosting providers, while app operators patch the infrastructure they control.

Was merchant data leaked in the Thalia incident?

Based on the available server logs reviewed by Thalia, no evidence was found that merchant data was accessed or leaked in connection with this issue. That is an investigation finding for the affected environment, not an absolute statement about every PHP installation.

Conclusion

PHP2Shell was a runtime-level security issue that required a runtime-level fix. Thalia responded by upgrading PHP 8.3.22 to PHP 8.3.36, applying the required patches across the affected product environment, verifying normal application behavior, and reviewing available logs.

For merchants, the practical answer is simple: no action is required, existing data and settings were not changed, and the applications can continue to be used normally. For engineering teams, the lasting lesson is to know where the runtime is running, patch the component actually exposed, verify the live process, and communicate findings with evidence-based language.
